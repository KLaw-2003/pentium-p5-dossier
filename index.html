1. Overview

The Intel Pentium P5, introduced in 1993, is a 32-bit x86 superscalar processor. It preserves x86 binary compatibility while adding two integer execution pipelines, dynamic branch prediction, split instruction and data caches, and a pipelined floating-point unit. The integer core uses in-order, dual-issue execution: up to two adjacent instructions may be issued in one cycle when the pairing rules are satisfied.[1]

2. Microarchitecture

U and V integer pipelines

Pentium duplicates key address-generation and integer execution resources to form two pipelines, U and V. The pipelines are asymmetric: U can execute a broader class of instructions, while V is restricted to simpler operations. When a legal pair is found, the first instruction is issued to U and the second to V.[1]

Register file organization

The processor retains the x86 architectural integer register model, including the eight 32-bit general-purpose registers EAX, EBX, ECX, EDX, ESI, EDI, EBP, and ESP. The U and V pipelines share the same architectural register state, so register dependencies directly constrain whether two instructions can be paired.[2]

Branch prediction

Pentium uses a dynamic branch predictor with a 256-entry, four-way set-associative Branch Target Buffer (BTB). The BTB stores branch target and history information so that the front end can continue fetching along a predicted path. A correct prediction avoids the normal taken-branch delay; a misprediction redirects fetching and discards work from the wrong path.[1]

3. ISA Features

Pentium does not introduce a new ISA; it implements the existing x86 ISA. Several x86 characteristics are especially important because they make wide fetch, decode, and superscalar issue more difficult.

  • Variable-length instructions. The front end must identify instruction boundaries before it can decode two instructions together.
  • Complex addressing modes. Memory operands require address generation in addition to the arithmetic or logical operation.
  • Hardwired and microcoded instructions. A “simple” instruction can be handled directly by normal hardwired pipeline control; more complex instructions require a microcode sequence.[1]
  • Backward compatibility. The internal microarchitecture changes substantially while the software-visible x86 behavior remains compatible with existing binaries.

The architecture paper reports that more than 90% of dynamically executed instructions in the Integer SPEC workloads were in the “simple” class.[1]

Instruction pairing

Pentium considers two consecutive instructions, I1 and I2. A normal pair requires:

  • both instructions are simple,
  • I1 is not a jump,
  • no RAW (read-after-write) dependency from I1 to I2,
  • no WAW (write-after-write) dependency, and
  • the required execution resources are compatible with the U/V organization.

If the checks fail, I1 issues alone; the in-order issue logic does not skip I2 to search farther ahead for a better pair. Compiler scheduling can therefore improve performance by placing independent instructions next to each other before execution.[1]

Precise exceptions

A precise exception leaves the architectural state corresponding to a well-defined point in program order: instructions before the faulting instruction appear completed, while later instructions have not changed visible state. In the Pentium integer pipeline, exceptional conditions must be resolved before an instruction is allowed to update registers and flags in the WB stage.[1]

Why the caches are split

The i486 used a single unified cache, and the Pentium authors are explicit that a unified cache is the better design on its own terms: at equal capacity it achieves a higher hit rate because it balances code and data lines automatically, only one cache has to be designed, and self-modifying code is simpler to handle.[1]

Pentium splits the cache anyway, because superscalar issue and branch prediction demand more bandwidth than one port can supply. A predicted-taken branch must fetch its target while earlier instructions are still accessing data; two paired memory instructions may need a load and a store in the same cycle; and with the rest of the Pentium design in place, keeping split caches consistent for self-modifying code turned out to be only marginally more complex. The split therefore buys ports, not capacity — Intel traded hit rate for bandwidth deliberately.[1]

A small data cache is defensible for x86 because x86 code generates far more data references than RISC code: measurements on the Integer SPEC benchmarks show 0.5–0.6 data references per instruction on the i486 against 0.17–0.33 on a MIPS processor, a direct consequence of having only eight general-purpose registers and passing procedure parameters in memory. Those extra references fit in a RISC register file, so their locality is tight enough for 8 KB to capture them.[1]

Dual-access data cache

The data cache must answer two addresses per cycle, one from each pipeline, and it does so asymmetrically. The address path is fully dual-ported: the TLB and the cache tags accept both the U-pipe and V-pipe addresses in the same cycle. The data path is single-ported and divided into eight interleaved 32-bit banks. Two accesses that fall in different banks complete in the same clock; if both fall in the same bank, the U pipe takes priority and the V pipe stalls for one clock. For double-precision floating-point operands, two consecutive banks are accessed in parallel to form a single 64-bit path.[1]

The bank-conflict logic does double duty. Two references to the same address necessarily map to the same bank, so they are serialized automatically — which is how the resource and data dependencies between memory references, deliberately not resolved by the D1 issue logic, are resolved at all.[1]

Important: successful pairing in D1 does not guarantee stall-free execution later in the pipeline. Pairing is decided in D1 from opcode and register operands alone; effective addresses are not produced until D2, so whether the pair actually completes without a stall is settled two stages later, in E, by the bank-conflict logic.

The design team evaluated a fully dual-ported data array and rejected it. Dual porting eliminates bank conflicts, but the SRAM cell is larger, so the same silicon area yields a smaller cache and a lower hit ratio, and dependency handling becomes more complex. Interleaving was chosen as the better trade of an occasional one-cycle conflict against capacity.[1]

Address translation and write buffers

Virtual addresses are translated before a cache lookup can complete, so a translation lookaside buffer (TLB) sits on the address path shown above. Pentium provides separate TLBs for the instruction and data caches, with additional entries covering the 4 MB page size introduced by P5; the vendor documentation gives the entry counts and associativities.[2] Pentium also contains write buffers, which decouple the pipelines from the external bus and which the memory-ordering rules below explicitly refer to.[3]

Cache hierarchy beyond L1

P5 integrates only the two L1 caches. There is no on-die L2; in Pentium systems of this generation, second-level cache is external, implemented on the motherboard and managed by the chipset, and is reached over the processor's 64-bit external data bus. A 32-byte line is therefore filled by a burst of four 64-bit transfers.[2]

Cache coherence: write-back and MESI

Cache coherence and the memory consistency model are different things: coherence governs what values a single location may return across caches, while the consistency model governs the ordering software may observe across different locations. Pentium's coherence mechanism is a write-back protocol with four states — modified, exclusive, shared, and invalid (MESI), a change from the i486's write-through policy.[1]

The motivation is bus bandwidth. With a write-through protocol and a 32-bit data bus, the i486DX2 occupies the bus 80% of the time, and 85% of all bus cycles are writes. Given Pentium's faster core pipelines and 64-bit data bus, moving to write-back was, in the authors' words, an obvious enhancement.[1]

The same mechanisms that maintain consistency with external memory also maintain consistency between the code cache and the data cache. This matters for x86 compatibility: self-modifying code must observe the updated instruction, so dedicated logic checks the pipeline for a store to an instruction that has already been fetched — including instructions reached through a branch predicted by the BTB — and flushes incorrectly fetched instructions when necessary.[1]

Memory consistency model (MCM)

The memory consistency model defines the ordering of memory operations that software may observe. Intel describes the Pentium and Intel486 as following a processor-ordered memory model, while behaving as strongly ordered processors in most circumstances. Reads and writes normally appear at the system bus in program order, with a documented exception: a read miss may pass buffered writes when those writes are cache hits and are not to the address of the read miss. I/O reads and writes remain in program order.[3]

That exception is a direct consequence of the write buffers: allowing a read miss to bypass buffered writes hides write latency, at the cost of a model slightly weaker than sequential consistency. Software that requires stronger ordering uses locked operations (the LOCK prefix) or serializing instructions.[3]

6. Performance Characterization

The architecture paper reports approximately 2× integer performance over the i486 in an equal-core-clock comparison and substantially larger floating-point gains. In the SPEC92 chart discussed in our presentation, the Pentium/i486DX2-66 ratios are approximately 2.0× for SPECint92 and 3.6× for SPECfp92; the paper separately reports gains of up to about 5× on some floating-point vector code.[1]

These gains should not be attributed to dual issue alone. They also reflect branch prediction, the split caches, a wider memory interface, the pipelined FPU, compiler scheduling, and workload characteristics. In practice, the theoretical two-instruction issue width is reduced by pairing restrictions, branches, cache misses, and bank conflicts.

7. Discussion Questions

  1. Why did Pentium use asymmetric U and V pipelines instead of two identical integer pipelines?
  2. How much benefit can dual issue provide when the processor can only pair adjacent instructions?
  3. Pentium rejected a fully dual-ported data array in favour of eight interleaved single-ported banks, accepting occasional one-cycle stalls to keep the cache large. Under what workload would that trade have been the wrong call?
